# BabyTrack Design Guidelines

> **Our Standard**: Apple's simplicity. Nokia's reliability. F1's speed.

---

## Core Philosophy

**"A sleep-deprived parent at 3am, holding a baby with one hand, should see their baby's vitals in under 3 seconds."**

Every design decision flows from this.

---

## 1. Apple-Like Simplicity
> "If it needs explanation, redesign it."

### Rules
- Every screen has **ONE primary action**
- Remove until it breaks, then add back one thing
- Animations are **purposeful**, not decorative
- Touch targets minimum **44x44px**
- White space is a feature, not wasted space
- No tooltips - if you need to explain, redesign

### Anti-Patterns (Never Do)
- ❌ Multiple CTAs competing for attention
- ❌ Dense information walls
- ❌ Hidden gestures without discovery
- ❌ Nested menus deeper than 2 levels

---

## 2. Nokia-Level Reliability
> "It just works. Always."

### Standards
- App opens in **< 2 seconds** - every time
- **Zero crashes** in production
- Offline mode works seamlessly
- Graceful degradation (no internet → show cached data)
- Battery efficient - no background drain
- Works on 3-year-old devices

### Error Handling
- Every error has a **user-friendly message**
- Every error has a **recovery action**
- Never show stack traces or technical errors
- Log everything for debugging, show nothing scary

### Testing Requirements
- Unit tests for all business logic
- Widget tests for all screens
- Integration tests for critical flows
- Performance tests for every release

## 5. Parent-First UX
> "Design for 3am with one hand."

### One-Handed Use
- Primary actions in **thumb zone** (bottom 60% of screen)
- Navigation at bottom, not top
- No precise gestures required
- Swipe actions have button alternatives

### Low-Light Friendly
- High contrast ratios (4.5:1 minimum)
- Dark mode support
- No pure white (#FFFFFF) in dark mode
- Status colors visible in dim light

### Minimal Cognitive Load
- No typing for common actions
- Recognition over recall
- Consistent patterns across screens
- Undo available for destructive actions

### Haptic Language
```
Light:  Navigation, selection
Medium: Success confirmation
Heavy:  Error, warning
```

## 6. Zero Tolerance for Bugs
> "Ship when ready, not when scheduled."

### Definition of Done
- [ ] Feature works as specified
- [ ] Edge cases handled
- [ ] Error states designed
- [ ] Loading states smooth
- [ ] Offline behavior defined
- [ ] Tests written and passing
- [ ] Performance budget met
- [ ] Accessibility checked
- [ ] Code reviewed

### Bug Classification
| Severity | Response Time | Example |
|----------|---------------|---------|
| P0 | < 4 hours | App crash, data loss |
| P1 | < 24 hours | Feature broken, wrong data |
| P2 | < 1 week | UI glitch, minor issue |
| P3 | Next sprint | Enhancement, polish |

### Code Quality
- No `// TODO: fix later` in production
- No commented-out code
- No magic numbers
- No functions > 50 lines
- No files > 500 lines

## 7. Fastest in the World
> "Speed is a feature. Lag is a bug."

### Hard Limits (Non-Negotiable)

| Metric | Target | Unacceptable | Measurement |
|--------|--------|--------------|-------------|
| Cold start | < 1.5s | > 3s | Time to interactive |
| Screen transition | < 200ms | > 400ms | Animation complete |
| Touch response | < 50ms | > 100ms | Visual feedback |
| API response feel | < 300ms | > 1s | Perceived complete |
| Frame rate | 60fps | < 55fps | Steady state |
| App size | < 30MB | > 50MB | Download size |
| RAM usage | < 150MB | > 250MB | Active usage |
| Battery drain | < 2%/hr | > 5%/hr | Active usage |

### The 3-Second Rule
```
App Launch → Baby's Vitals Visible
         < 3 SECONDS
```

Not login. Not loading. **THE DATA.**

### Performance Rules

**1. NO JANK - Ever**
- List scrolling = butter smooth
- Animations never drop frames
- Loading states, not frozen UI
- 60fps or fix it before shipping

**2. INSTANT FEEDBACK**
- Touch → visual response in 16ms (1 frame)
- Optimistic UI (assume success, rollback on failure)
- Skeleton screens over spinners
- Progress indicators for > 1s operations

**3. LAZY EVERYTHING**
- Load only what's visible
- Prefetch what's likely next
- Cache aggressively (images, API responses)
- Paginate lists (never load 1000 items)

**4. MEASURE OBSESSIVELY**
- Performance monitoring in production
- Regression = release blocker
- Budget per feature (CPU, memory, battery)
- Weekly performance review

### Optimization Checklist
- [ ] Images optimized and cached
- [ ] Lists use virtualization
- [ ] Heavy computation off main thread
- [ ] Unnecessary rebuilds eliminated
- [ ] Network requests batched
- [ ] Animations use native driver

## Implementation Checklist

### Every Screen Must Have
- [ ] Loading state (skeleton)
- [ ] Empty state (helpful message + action)
- [ ] Error state (friendly message + retry)
- [ ] Offline state (cached data or message)
- [ ] Pull-to-refresh where applicable

### Every Button Must Have
- [ ] Disabled state (visual + functional)
- [ ] Loading state (spinner, no double-tap)
- [ ] Pressed state (visual feedback)
- [ ] Minimum 44x44px touch target

### Every Input Must Have
- [ ] Label (always visible)
- [ ] Placeholder (example, not instruction)
- [ ] Error state (red border + message below)
- [ ] Success state where applicable
- [ ] Keyboard type optimized

### Every List Must Have
- [ ] Virtualization (only render visible)
- [ ] Pull-to-refresh
- [ ] Empty state
- [ ] Loading state (skeletons)
- [ ] Error state with retry
